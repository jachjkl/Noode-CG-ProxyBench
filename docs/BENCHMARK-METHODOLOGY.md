# Measurement methodology

## Proxy method

Every acquired candidate enters actual website testing without a preliminary direct-port probe. Each IP attempts Google, Cloudflare and GitHub once through its authenticated named outbound in an isolated rule-mode Mihomo core. The three response-header latencies are summed and divided by three. No warmup, repeated requests, trimming or delay fallback occurs. A failed request stays a failure, contributes its configured timeout value to the mean, and is counted against the saved failure-rate limit. Missing or duplicate site observations are rejected. One observation per site cannot establish temporal jitter; the UI shows it as unavailable and the obsolete multi-round jitter/cooldown options are retired.

Website response timing begins after connection and named-route verification and ends at headers. Google and GitHub use HEAD; Cloudflare trace uses GET with HTTP 200 and trace-body validation. The complete site operation, including connection and route verification, has the saved request timeout as its total deadline. Controller proof polling shares that budget and never silently uses the former default ten-second waits. A socket watchdog also interrupts peers that keep sending partial headers or bodies. Every IP attempts all three sites even after an earlier failure.

The original-package small-sample speed method reads a bounded 512 KiB body through the selected candidate, requiring 95% completion, the saved minimum Mbps, an 8-second I/O timeout and a 7-second body-time limit by default. Connect/proof, header and body operations have independent bounded deadlines matching their specified limits. A download cannot qualify after its body deadline even if enough bytes have arrived. Geography queries also honor their configured deadline. Named inbounds and routing evidence prevent selector races; the existing system proxy, VPN and TUN remain unchanged. Adaptive concurrency stays within the saved upper bound and reduces genuine congestion without changing quality thresholds.

## Direct TCP/TLS method

Select exactly one latency method: TCPing or TLS. TCPing directly connects to the candidate IP and port three consecutive times. TLS instead performs three verified handshakes using the project's configured target-domain SNI, including connection and handshake time; there is no separate TCP latency gate. Average latency and population-standard-deviation jitter use successful samples. Loss is failed attempts divided by all three attempts. A timeout remains a failure; all three attempts are recorded. Saved latency, loss and jitter limits apply to the selected method. HTTPS download always uses TLS transport, even when TCPing is the latency method.

Keep the reference probe implementations but apply the owner's latest batch rule: 100 candidates complete their selected three-sample latency test, then survivors complete the original download probe before the next group starts. Latency and speed phases do not overlap. This avoids the previous complete-pool TCP screening and delays in displaying qualified candidates. Source ordering and the Japanese hint priority are preserved, and final winners still compete under fresh measurements. The previous direct-policy cache is archived and its measurements revoked; candidates and session history remain available for fresh testing. Changing the latency choice while its task is running is rejected.

Direct speed uses the original pinned-IP probe with `speed.cloudflare.com` SNI, the configured sample size and strict body completeness/timeout/speed limits. It never loads proxy authentication, changes the system proxy or creates an application proxy core. Existing operating-system routes still apply. Trace `colo` supplies an edge location from the bundled mapping; client `loc` is ignored. Unknown geography cannot qualify for the additional Japanese quota.

Version 1.2.3 moves UI updates and result persistence off the network measurement threads. A single ordered observer persists every completed record, coalesces preview updates, drains before commit/stop, and propagates I/O failures. No record is accepted from a preview snapshot. This prevents synchronous disk/UI work from stretching concurrent TCP/TLS elapsed times. Proxy observers use the same separation. Direct defaults now match the reference package's effective local parallelism: 100 TLS workers, 20 download workers, and a one-second TCP timeout. The exact legacy preset of 32 TLS / 4 download / 1.2-second TCP is migrated once; quality limits and counts stay unchanged, and nondefault custom settings remain authoritative. Direct download concurrency supports 1–20.

## Competition and output

Proxy and direct methods separately save ordinary and Japanese publication counts. Their new shortlists and previous cloud results compete under fresh measurements, including all three samples of the currently selected direct latency method. Failed retests replace stale passes. Saved-rule changes restart final competition. Rank proxy results by loss, successful observations, trimmed composite, jitter, speed and stable address tie-breakers. Rank direct results by the selected method's loss, average, jitter, speed and stable address tie-breakers. Reserve the best eligible Japanese append candidates, select the ordinary quota, then append unique Japanese winners.

Automatic output requires all configured slots. Explicit manual output may contain fewer qualified addresses, with actual counts recorded in health metadata. Both local packing and Ubuntu decoding verify namespace, mode, quotas, uniqueness, ranks, text consistency and the full output set. Proxy files use `output/`; direct metadata uses `output/Nodes-TCP/`, while TCPing and TLS share the public text subscription `output/Npdex-Tcp/Tls.txt`. Its bytes must match the ranked direct metadata before any cloud writes. A failed publication preserves it, local transactions include it in rollback, and legacy direct archives regenerate it from their validated text. Neither direct method modifies the proxy subscription.

## Batch lifecycle and core versions (1.2.4)

Both engines use fixed 100-IP batches, with all remaining candidates in the final short batch. There is no preliminary screening API or optional admission stage. Direct TCPing and TLS still perform their selected three-attempt observations on every candidate, then apply saved latency/loss/jitter limits before downloading for latency-qualified candidates. A proxy failure is based on actual named-proxy website evidence, never a raw TCP entrance test. Explicit stop/pause/manual publication controls remain available.

After the ordered observer drains, address-only outcome markers and qualified details are committed atomically. Failed bodies and the partial journal are removed, active previews are cleared, and the owned proxy core unloads its batch listeners and closes its connections before the next group. Failed competition measurements also invalidate stale ordinary passes. The lightweight ledger is session-local, retained only for abnormal recovery and discarded on normal closure; saved rules, logs, published output and qualified saved measurements persist.

Both choices review official stable core updates at window opening and before a run. Direct review validates the binary without starting any proxy core. Verified updates rotate only current and previous binary slots; the engine-card menu can swap them or restore automatic updates. Saved rollback selection does not skip release checks but prevents immediate replacement by the same release. Runtime-active switches are forbidden. Official asset and previous-binary SHA-256 checks, failed-update rollback and failed-selection rollback protect the installed version.


## Progress and bounded waits (1.2.5)

An address becomes completed only after actual measurement and ordered result persistence; latency progress remains distinct from final download qualification. Every batch exposes its input count, completed/qualified count, request count and compact per-IP status. The cleanup phase is written before compaction and listener removal. After cleanup, the progress bar and cells reset, including before the final short batch. Lightweight tested-address outcomes still prevent duplicate work after an abnormal resume.

The observer emits progress between ordered completion callbacks, preventing a fast completion burst from starving live updates. Network and UI/checkpoint I/O remain separate. The dashboard does not serialize unused full previews in state responses, caches only hash-verified unchanged checkpoints, and aborts/retries stalled browser reads. Direct TCP/TLS probes and geographic requests receive an outer deadline as well as their underlying network timeout. Saved latency, loss, speed and timeout limits are never increased to obtain more passes.
